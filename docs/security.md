# Gotham Command — Security Architecture & Hardening Guide

## 1. Authentication Architecture Overview

Gotham Command employs a secure, modern, hybrid token architecture tailored for single-page applications (SPA) communicating with a Spring Boot REST backend:
- **Authentication Authority**: Spring Security with Google OAuth 2.0.
- **Short-Lived Access Tokens**: Signed JSON Web Tokens (JWT) kept exclusively **in memory** by the React application.
- **Long-Lived Refresh Tokens**: Cryptographically random, opaque, server-persisted tokens stored in **HttpOnly, SameSite, Secure** cookies.

```
┌───────────────┐               ┌────────────────────┐               ┌────────────────┐
│ React/Vite UI │               │ Spring Boot Server │               │ Google OAuth2  │
└───────┬───────┘               └─────────┬──────────┘               └───────┬────────┘
        │                                 │                                  │
        │  1. Initiate Google Login       │                                  │
        ├────────────────────────────────►│  2. Redirect to Google           │
        │                                 ├─────────────────────────────────►│
        │                                 │  3. Authenticate User            │
```

## 2. Google OAuth 2.0 Flow & Zero-Token URL Policy

Prior iterations passed authorization tokens via URL query parameters (`?token=...`), which exposed them to:
- Browser history logs
- Referrer headers
- Shoulder surfing / screen recordings
- Proxy/gateway access logs

### Hardened OAuth Callback:
1. When user authenticates with Google, Spring Security's `OAuth2AuthenticationSuccessHandler` validates or provisions the `User`.
2. A cryptographically random refresh token is generated and persisted in PostgreSQL.
3. The server issues an `HttpOnly` cookie containing the refresh token (`gotham_refresh_token`).
4. The server redirects the browser to `https://<frontend>/auth/callback?auth=success`.
5. **No access token, refresh token, or sensitive secret is ever placed in the URL query parameters or hash fragments.**
6. On error, the handler redirects to `https://<frontend>/auth/callback?error=authentication_failed` without disclosing internal stack traces, database schema details, or exception messages.

## 3. JWT Access Token Security

- **Storage**: In-memory JavaScript runtime only (`client/src/services/api.ts`).
- **Never Persisted**: The access token is **never** written to `localStorage`, `sessionStorage`, or indexedDB. A full page reload silently exchanges the HttpOnly refresh cookie for a fresh access token.
- **Payload Minimality**: Contains only safe claims:
  - `sub`: User UUID
  - `email`: User email address
  - `roles`: Authority list (e.g., `["ROLE_USER"]`)
  - `iat`: Issued-at timestamp
  - `exp`: Expiration timestamp (default 15 minutes / configurable)
  - No passwords, secrets, OAuth tokens, or database credentials are ever included in claims.
- **Cryptographic Verification**: Validated on every protected request by `JwtAuthenticationFilter` via HMAC-SHA256 signature verification using `verifyWith(getSigningKey())`.

## 4. Refresh Token Architecture & Lifecycle

- **Opaque & Cryptographically Random**: Generated by `RefreshTokenService` using Java's `SecureRandom` (48 high-entropy random bytes, Base64URL-encoded).
- **Server-Side Persistence**: Every token is tracked in the `refresh_tokens` database table with its owning `user_id`, `expires_at`, `revoked` flag, and `revoked_at` timestamp.
- **Token Rotation**: Every call to `POST /api/auth/refresh` immediately revokes the current token (`revoked = true`, `revoked_at = NOW()`) and issues a brand-new refresh token.
- **Revocation on Logout**: `POST /api/auth/logout` revokes the token in PostgreSQL and clears the browser cookie (`maxAge = 0`).
- **Inaccessible to JavaScript**: The refresh token is omitted from the JSON response body (`TokenResponse`) and is transported solely via the browser's native cookie handling.

## 5. Cookie Security Configuration

The refresh cookie is configured via Spring's `ResponseCookie`:
```yaml
app:
  auth:
    cookie:
      name: gotham_refresh_token
      secure: ${REFRESH_COOKIE_SECURE:false} # true in production (HTTPS)
      same-site: Lax
      path: /api/auth
      max-age-seconds: 604800 # 7 days
```
- **HttpOnly = true**: Inaccessible via `document.cookie` in JavaScript, eliminating token theft via Cross-Site Scripting (XSS).
- **Path = /api/auth**: Sent only on requests to `/api/auth/refresh` and `/api/auth/logout`, never sent on general API requests or static asset fetches.
- **SameSite = Lax**: Mitigates Cross-Site Request Forgery (CSRF) by preventing cookie inclusion on cross-site requests.
- **Secure**: Configurable via `REFRESH_COOKIE_SECURE`; enabled in production to guarantee HTTPS transport.

## 6. Cross-Origin Resource Sharing (CORS)

Configured strictly in `SecurityConfig.java`:
- **Explicit Origins Only**: Origins are restricted to trusted domains defined via `cors.allowed-origins` (e.g., `http://localhost:5173`, production domains).
- **No Wildcarding with Credentials**: `allowedOrigins("*")` is explicitly avoided when `allowCredentials(true)` is enabled, complying with modern browser security specifications.
- **Allowed Methods**: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`.
- **Allowed Headers**: `Authorization`, `Content-Type`, `X-Requested-With`, `Accept`.

---

## 7. CSRF Architecture & Rationale

- **REST API Endpoints**: Stateless and authenticated strictly via the `Authorization: Bearer <jwt>` HTTP header. Because browsers never automatically attach custom `Authorization` headers to cross-site requests, standard REST endpoints are immune to CSRF by design.
- **Cookie-Based Endpoints (`/api/auth/refresh`, `/api/auth/logout`)**: Protected by:
  1. `SameSite=Lax` cookie policy, which suppresses cookies on cross-origin POST requests.
  2. CORS preflight validation, rejecting requests originating from non-whitelisted origins.
  3. Single-origin deployment in Docker/Nginx where frontend and API reverse-proxy through a unified domain.

## 8. Role-Based Access Control (RBAC)

Gotham Command enforces a 5-tier hierarchical authorization model at both service and database levels:

| Role | Scope | Key Permissions |
| :--- | :--- | :--- |
| **SUPER_ADMIN** | System-Wide | Platform governance, cross-tenant oversight, role administration. |
| **ORG_ADMIN** | Organization | Manage organization, invite/remove members, manage projects, assign roles. |
| **PROJECT_MANAGER**| Project | Create, edit, delete projects and project issues; assign project members. |
| **MEMBER** | Project | Create issues, edit assigned issues, add comments, move board statuses. |
| **VIEWER** | Project | Read-only access to projects, issues, comments. Mutations blocked with 403. |

- Self-demotion protection: An `ORG_ADMIN` cannot remove their own admin privileges if they are the last administrator.
- Elevation protection: An `ORG_ADMIN` cannot elevate any user to `SUPER_ADMIN`.

---

## 9. Tenant Isolation & Cascade Security

- Multi-tenant boundary is enforced per Organization (`organizations` table).
- All resource queries traverse the hierarchy: `Issue` → `Project` → `Organization`.
- Users cannot access, view, or mutate issues or projects in organizations where they hold no active membership.
- Deleting an organization cascades cleanly to its projects, issues, comments, and memberships, leaving zero orphaned records.

## 10. HTTP Security Headers

Both Spring Boot (`SecurityConfig.java`) and the Nginx reverse proxy (`nginx.conf`) emit defense-in-depth HTTP security headers:
- `X-Frame-Options: DENY`: Prevents clickjacking attacks by forbidding iframe embedding.
- `X-Content-Type-Options: nosniff`: Prevents MIME-type sniffing.
- `Referrer-Policy: strict-origin-when-cross-origin`: Restricts referrer information sent with outbound requests.
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`: Disables access to sensitive browser device features.

### Content Security Policy (CSP) Analysis & Operational Recommendation
In single-page applications with dynamic client-side rendering (Vite + React), Google OAuth redirection, and external web fonts, introducing a naive or overly restrictive Content Security Policy header often causes production regressions:
1. **Google OAuth 2.0 & Accounts**: Redirecting to `accounts.google.com` requires script and connect policies that do not inhibit Google Identity services or credential callbacks.
2. **Vite Dynamic Chunking & Inline Styles**: CSS-in-JS and Tailwind utilities often utilize inline styles or dynamic module imports that fail unless cryptographic script/style nonces or hashes are generated dynamically per request by a specialized edge proxy.
3. **Operational Recommendation**: Rather than applying a blanket, brittle CSP that could break authentication or UI asset loading in unknown deployment environments, production deployments should configure CSP at the edge reverse proxy / CDN with nonces specifically tuned to the production domain and Google OAuth identity providers.

## 11. Backend Exception Handling & Data Sanitization

`GlobalExceptionHandler.java` catches all exceptions and normalizes them to sanitized responses:
- `400 BAD_REQUEST`: Validation errors or illegal arguments without leaking internal code paths.
- `401 UNAUTHORIZED`: Authentication failure / missing token.
- `403 FORBIDDEN`: Authorization / RBAC access denied.
- `404 NOT_FOUND`: Resource not found.
- `409 CONFLICT`: `DataIntegrityViolationException` intercepts duplicate keys and foreign-key constraints without exposing raw PostgreSQL error strings or table definitions.
- `500 INTERNAL_SERVER_ERROR`: Unhandled exceptions log full details internally via SLF4J while returning a generic `"An internal error occurred."` message to the caller.

## 12. Secret Management & Environment Variables

- **Client-Safe Variables**: Prefixed with `VITE_` (e.g., `VITE_API_URL`, `VITE_BACKEND_URL`).
- **Server Secrets**:
  - `JWT_SECRET`: 256+ bit secret used for HMAC-SHA256 signing.
  - `GOOGLE_CLIENT_ID` & `GOOGLE_CLIENT_SECRET`: Managed securely via environment variables.
  - `DATABASE_USERNAME` & `DATABASE_PASSWORD`: Supplied to PostgreSQL and Spring Boot via environment variables.
- All secrets are excluded from source control via `.gitignore`.
- Vite bundler is configured to never ingest or bundle server secrets.

---

## 13. Production Deployment Recommendations

1. **Enforce HTTPS**: Set `REFRESH_COOKIE_SECURE=true` and terminate TLS at the Nginx reverse proxy or cloud load balancer.
2. **Rotate Secrets**: Regularly rotate `JWT_SECRET` and Google OAuth credentials.
3. **Database Security**: Keep PostgreSQL on a private Docker bridge network without exposing port 5432 to the public internet.
4. **Flyway Migrations**: Maintain `spring.jpa.hibernate.ddl-auto=validate` so Hibernate never modifies schemas automatically in production.
